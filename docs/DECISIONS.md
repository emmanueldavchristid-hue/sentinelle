# Décisions

- **D-01 (15/11)** — Code destiné au concours en attente : l'autorisation du développement préalable n'est pas confirmée. L'usage de l'IA est autorisé, ce qui n'autorise pas le code préparé. Seuls cadrage, scénario, maquettes et spécifications de tests sont produits.
- **D-02 (15/11)** — Stack validée par le porteur : monorepo pnpm TypeScript ; moteur pur `packages/domain` ; contrats Zod ; API Fastify ; PostgreSQL ; React + Vite + Tailwind ; Dexie (IndexedDB) ; Vitest ; Playwright ; schéma SVG (pas de carte externe).
- **D-03 (15/11)** — Historique des analyses : **instantané des données utilisées** stocké avec chaque analyse (JSON des enregistrements pris en compte, avec leur identifiant et numéro de révision) + `snapshotHash` + `engineVersion` + paramètres. En parallèle, les corrections créent des révisions en ajout seul (jamais d'écrasement). Ce que cela permet réellement : relire une ancienne analyse exactement telle qu'elle a été calculée, et la recalculer à l'identique avec la même version du moteur. Ce que cela ne permet pas : reconstituer l'état complet de la base à une date donnée (hors données incluses dans l'instantané). Choisi car plus simple que des requêtes « à la révision N » sur toutes les tables.
- **D-04 (15/11)** — Authentification : sélecteur de rôle nommé « mode démonstration ». Interdit de mise en ligne publique avec ce seul mécanisme.
- **D-05 (15/11)** — IA du produit : aucune API payante. Saisie manuelle complète. Seule une interface `StructuringProvider` remplaçable est prévue, sans implémentation simulée présentée comme réelle.
- **D-06 (15/11)** — Démo sur un ordinateur Windows avec Docker déclaré installé (fonctionnement non vérifié). PostgreSQL via Docker Compose par défaut ; alternative documentée : PostgreSQL installé nativement sous Windows. Scripts en `pnpm`/Node, pas de scripts bash obligatoires.
- **D-07 (15/11)** — Temps : stockage UTC, affichage `Africa/Abidjan`, intervalles semi-ouverts, précision explicite (`INSTANT`/`DAY`/`INTERVAL`/`UNKNOWN`), jamais de minuit implicite.
- **D-08 (15/11)** — Profondeur d'analyse limitée à 2 pour la démonstration.
- **D-09 (15/11 19:35)** — Le porteur décide de lancer le développement maintenant (« vas-y, termine le projet »). L'autorisation des organisateurs pour le code préalable reste **non confirmée** : tout le code produit à partir de cette date doit être **déclaré comme travail préalable** aux organisateurs, ou mis de côté si le règlement l'interdit.
- **D-10 (15/11)** — Base de données : PostgreSQL embarqué (PGlite, Postgres compilé en WebAssembly, fichiers dans `data/`) par défaut, pour démarrer sous Windows sans Docker ; PostgreSQL serveur (Docker Compose ou natif) via `DATABASE_URL`. Même SQL, migrations SQL versionnées maison (une seule solution). Le démon Docker n'est pas disponible dans l'environnement Claude : la voie Docker est **non vérifiée**.
- **D-11 (15/11)** — Hors connexion en démo : statut de connexion déterminé par un appel réel à `/api/health`. Un interrupteur « Couper le réseau (simulation démo) » bloque les appels côté client ; il est nommé comme une simulation. Le vrai mode hors ligne (DevTools / mode avion) reste possible grâce au service worker.
- **D-12 (15/11 21:10)** — Finition demandée par le porteur (« finis complètement le projet », démo P0 jugée prête). Ajouts sans toucher au parcours de démonstration.
- **D-13 (15/11)** — Mode authentifié (`DEMO_MODE=false`) : comptes créés en ligne de commande (`pnpm user:create`, mot de passe lu sur l'entrée standard, 12 caractères min.), hachage scrypt, session par cookie httpOnly SameSite=Strict (seul le hachage du jeton est stocké), verrouillage après 5 échecs pendant 15 min, contrôle de l'en-tête Origin, en-têtes de sécurité (CSP…). Le sélecteur de rôle et la réinitialisation sont alors désactivés. Reste nécessaire avant toute mise en ligne : HTTPS, `COOKIE_SECURE=true`, revue de sécurité, sauvegardes, gestion des comptes (désactivation, renouvellement de mot de passe).
- **D-14 (15/11)** — Import CSV : prévisualisation ligne par ligne, import tout-ou-rien, idempotent, refusé si le fichier a changé depuis la prévisualisation ; un enregistrement existant ne se remplace pas par import (correction = révision) ; animal inconnu créé avec avertissement, lieu inconnu = erreur. Réservé au vétérinaire.
- **D-15 (15/11)** — Aide IA : désactivée par défaut. Fournisseur Anthropic activable côté serveur par `AI_PROVIDER=anthropic` + `ANTHROPIC_API_KEY` (aucune clé fournie, appel réel **jamais exécuté** dans ce projet). Timeout, taille limitée, plafond quotidien, sortie validée par schéma strict et recoupée avec le périmètre, confirmation humaine obligatoire. Pas de mode « exemples préenregistrés ».
- **D-16 (15/11)** — Corrections étendues aux mouvements (traitement des anomalies). QR : raccourci vers la fiche (lien interne uniquement), lecture via l'API BarcodeDetector si le navigateur la fournit, sinon repli sur la recherche manuelle.
- **D-17 (17/11)** — Le porteur demande de terminer toute l'application, y compris l'IA, et autorise tout sans nouvelle question. Limites maintenues malgré cette autorisation : aucune dépense ni clé créée, aucune mise en ligne publique (le mode authentifié n'est pas prêt pour Internet, D-13), aucune fusion vers une branche `main` (inexistante).
- **D-18 (17/11)** — IA : client générique côté serveur, `anthropic` ou `openai-compatible` (OpenAI, Mistral, ou modèle local gratuit Ollama/LM Studio). Deux usages : aide à la saisie, reformulation de la synthèse. La synthèse **déterministe** reste la référence ; une reformulation n'est acceptée que si elle passe la vérification (identifiants existants, preuves autorisées, vocabulaire interdit) et elle est conservée avec son fournisseur. Formats de requête vérifiés contre de faux serveurs HTTP ; aucun appel à un vrai modèle effectué.
- **D-19 (17/11)** — Revue indépendante (sous-agent, lecture seule) : 0 critique, 4 importants, 6 mineurs. Tous corrigés et testés : idempotence limitée à (organisation, utilisateur, opération, cible, contenu) ; verrous transactionnels PostgreSQL (`pg_advisory_xact_lock`) pour analyses, révisions, enquêtes, imports ; réinitialisation démo protégée par en-tête personnalisé et Origin ; lieux suivants bornés par la fenêtre et le chevauchement ; bord de fenêtre strict ; présence d'arrivée choisie selon l'heure ; erreurs de paramètres en 400 ; quota IA par utilisateur ; purge des échecs de connexion ; déconnexion sans perte des déclarations non transmises.
- **D-20 (17/11)** — Exploitation : `db:backup`/`db:restore` (base embarquée, restauration non destructive), `user:list/disable/enable`, image Docker, intégration continue GitHub Actions (typage, tests PGlite, tests PostgreSQL serveur, navigateur, construction et démarrage de l'image).
- **D-21 (21/11)** — Nouvelle direction SENTINELLE VIVANT (brief `docs/BRIEF_SENTINELLE_VIVANT.md`) : l'éleveur est le premier utilisateur, l'application s'ouvre sur « Mon élevage aujourd'hui ». Branche `sentinelle-vivant` ; `feat/sentinelle-demo` garde la version du 20/11. Le moteur de mouvements et la console d'enquête restent intacts, réservés au vétérinaire.
- **D-22 (21/11)** — Une capacité = une fonction serveur validée (`apps/api/src/farm.ts`) appelée à la fois par les écrans et par l'assistant. Chaque résultat porte ses sources, ses dates, sa période et ses limites. L'assistant ne peut rien faire que l'interface ne sache déjà faire ; aucune écriture hors brouillon puis confirmation.
- **D-23 (21/11)** — « État des données » = instant de lecture donné par la base. « Ce qui a changé » entre deux états = enregistrements reçus par le serveur entre ces deux instants (observations, révisions, tâches). Plus simple qu'un instantané complet, et suffisant pour « Pourquoi ta réponse a changé ? ».
- **D-24 (21/11)** — Jeu vivant : couche d'événements synthétiques datés relativement au jour de la réinitialisation (`seed-living.ts`), sans toucher au scénario B-017. Rôle `FARMER` (migration 005).
- **D-25 (21/11)** — Assistant : Gemini par REST `generateContent` (pas de SDK ajouté), clé dans `sentinelle/.env` côté serveur uniquement. Modèle retenu après mesure réelle : `gemini-3.5-flash-lite`, secours `gemini-3.6-flash`. La documentation Google présente désormais une « Interactions API » comme interface par défaut ; `generateContent` reste pris en charge. Sans clé ou avec `ASSISTANT_AI=off`, lecture directe par règles fixes, annoncée comme telle. Pas d'autre fournisseur (la clé Groq reçue n'est pas utilisée).
- **D-26 (21/11)** — Lots, recherche documentaire, simulateur IoT : non commencés. Rien n'est affiché à leur sujet dans l'interface.
- **D-29 (21/11)** — Réponses à voix haute, demandées par Yvan pour les personnes qui ne lisent pas (éleveurs, agents, vétérinaires). Activées par défaut. La voix lit exactement le texte affiché (réponse, brouillon, reçu, alerte) : elle n'ajoute aucun fait et se dit « voix de synthèse ». Synthèse par Gemini via le serveur (`GEMINI_TTS_MODEL`), repli sur la voix de synthèse de l'appareil. Gemini assure la dictée et la voix : la clé Groq reçue n'est toujours pas utilisée, un seul fournisseur suffit.
- **D-28 (21/11)** — Balises de démonstration (idée de Mouhi : le PC sert de repère, un téléphone joue le capteur, alerte quand il s'éloigne, question et réponse à la voix). Retenu : contrat d'événement minimal (dispositif, source, instant observé, instant reçu, unité en mètres, précision, statut), un seul type de dispositif, pas de plateforme IoT. La distance est calculée sur le téléphone ; aucune coordonnée n'est transmise ni stockée. « Hors zone » seulement si le seuil est dépassé malgré la précision, sinon « incertain » ; une balise muette n'est pas dite sortie. Vocabulaire : « la balise associée à tel animal », jamais « l'animal s'évade ». Mode simulé conforme au brief (activation manuelle, bandeau permanent, source visible dans chaque preuve, arrêt simple). Écarté : notification par e-mail ou sur le téléphone (règle « pas de notification externe »), mesure réelle de quelques mètres en salle (hors de portée d'un GPS de téléphone).
- **D-27 (21/11)** — Voix : dictée plutôt que conversation en direct. Un enregistrement court, sur action explicite, transcrit par le modèle déjà configuré via un relais serveur, puis relu par l'utilisateur avant envoi. Raisons : stable et testable aujourd'hui (faux micro, vraie transcription), clé jamais dans le navigateur, pas d'écoute permanente, et la voix emprunte exactement le parcours du texte (brouillon puis confirmation). L'API Live (jetons éphémères, échange parlé continu) reste une suite possible, non commencée. Lecture des réponses par la voix de synthèse locale de l'appareil.
